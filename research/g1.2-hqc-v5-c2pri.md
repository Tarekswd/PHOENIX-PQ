# G1.2: Is HQC v5's KEM transform C2PRI?

Status: proof **sketch**, classical ROM only. Not peer reviewed. Date: 2026-11-04.

## Why the question is open

- Alagic, Bajaj, Kocoglu (ePrint 2025/1444, "ABK25") prove C2PRI for the FO variants U^⊥, U^⊥̸, U_m^⊥ and U_m^⊥̸ (their Theorem 5). They give a separate HQC theorem for the HQC transform of the **2024-10-30** specification (their Algorithm 16):
  - session key K = H(m, u, v);
  - coins from H_T(m, pk, salt);
  - rejection key H(s, u, v);
  - the salt is not bound into K.
- Krämer, Struck, Weishäupl (ePrint 2024/1233, CiC 2025; last revision 2025-07-04) analyse binding properties of round-4 HQC.
- HQC **v5.0.0 / v5.1.0** (specification 2025-08-22) use a different transform. It is in `src/common/hqc-kem.c` and `src/common/symmetric.c`, identical in v5.0.0 `kem.c`:

```
Encaps(ek):      m <- {0,1}^{8k}, salt <- {0,1}^{128}
                 (K || theta) = G(H(ek) || m || salt)          G = SHA3-512, domain byte dom_G
                 c_pke = PKE.Enc(ek, m; theta);  c = (c_pke, salt);  return (K, c)
Decaps(dk, c):   (seed_pke, sigma) = XOF(dk);  regenerate (ek, dk_pke)
                 m' = PKE.Dec(dk_pke, c_pke)
                 (K' || theta') = G(H(ek) || m' || salt)
                 K_bar = J(H(ek) || sigma || u || v || salt)    J = SHA3-256, domain byte dom_J
                 return K' if PKE.Enc(ek, m'; theta') == c_pke else K_bar
```

K is 32 bytes for all parameter sets (`CRYPTO_BYTES 32U`). Unlike the 2024 transform, K does not hash the ciphertext at all (as in ML-KEM), and the salt now enters both G and J. Neither ABK25's HQC theorem nor KSW covers this transform, so the published HQC-specific bound does not apply verbatim.

## Claim

Model G (first 256 output bits, written G_1) and J as independent random oracles; the domain bytes make them independent. Let an adversary get (ek, dk, c, K) with c honest and K = Decaps(dk, c), make q_G queries to G and q_J to J, and output c* ≠ c. Then

```
Pr[Decaps(dk, c*) = K]  <=  ((q_G + 2)^2 + (q_J + 2)^2) / 2^257  +  (q_G + q_J + 2) / 2^256
```

For example, with q_G = q_J = 2^64 the advantage is about 2^-128. Nothing is needed from the PKE except that encryption is a deterministic function of (ek, m, theta).

## Proof sketch

Write c = (c_pke, salt) and c* = (c*_pke, salt*). Say c "accepts" if the re-encryption check passes. There are four cases.

1. **c and c* both accept.** Then K = G_1(H(ek), m, salt) = G_1(H(ek), m*, salt*).
   - If (m*, salt*) = (m, salt), then theta* = theta, so c*_pke = Enc(ek, m*; theta*) = Enc(ek, m; theta) = c_pke, and c* = c. That is a contradiction.
   - So (m*, salt*) differs from (m, salt), and the adversary has found a G_1 collision among at most q_G + 2 inputs: probability at most (q_G + 2)^2 / 2^257.
2. **c accepts, c* rejects.** Then G_1(H(ek), m, salt) = J(H(ek), sigma, c*). The adversary knows sigma (it has dk), but each J query equals the fixed value K with probability 2^-256: at most (q_J + 1) / 2^256.
3. **c rejects, c* accepts.** This is the same as case 2 with the roles of G and J swapped: at most (q_G + 1) / 2^256.
4. **c and c* both reject.** Then J(H(ek), sigma, c) = J(H(ek), sigma, c*) with c ≠ c*. J hashes the whole of (u, v, salt), so this is a J collision: at most (q_J + 2)^2 / 2^257.

Summing the four cases gives the claim. The same argument works for decryption failures of c, since case 3 and case 4 do not assume that c decrypts correctly.

## Consequence for hybrid combiners (Direction 1)

If HQC v5 is C2PRI, ABK25's Theorem 8 lets a hybrid KEM drop the HQC ciphertext from its key-derivation input when it uses a split-key PRF, as X-Wing does for ML-KEM. For HQC-1 that is 4,433 bytes of ciphertext that would no longer be hashed per handshake (`CRYPTO_CIPHERTEXTBYTES 4433U`).

## What is NOT shown

- Quantum ROM. ABK25 handle U_m-style transforms with the one-way-to-hiding lemma; carrying that over is plausible but not done here.
- That SHA3-512 split into (K, theta) behaves as two independent random oracles. This is the standard heuristic, also used for ML-KEM.
- Whether the 2025-08-22 specification text matches the code. The code was checked (v5.0.0 and v5.1.0); the PDF specification was not.
- Peer review. This needs checking by a cryptographer before it is cited.
